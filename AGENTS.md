# yaHerd Engineering Instructions

These instructions apply to every code change in this repository.

## Engineering ownership

The coding agent owns the complete engineering process. The user is not responsible for separately requesting architecture review, regression analysis, tests, concurrency analysis, self-review, verification, commit decomposition, or pull-request decomposition.

Do not treat existing code as correct merely because it was previously generated by an AI agent. Review all relevant existing code as part of every change.

## Before editing code

Before making changes:

1. Inspect the current repository state, branch, and uncommitted changes.
2. Read the relevant implementation, tests, protocols, models, repositories, use cases, view models, and views.
3. Trace every production caller and mutation path affected by the requested change.
4. Identify affected boundaries, including where applicable:

   * SwiftData persistence
   * Core Data bridge persistence
   * CloudKit synchronization
   * collaboration ownership and permissions
   * cross-device convergence
   * concurrency and actor isolation
   * application mutation invalidation
   * navigation and state restoration
   * multi-window and scene behavior
   * accessibility
   * destructive actions and recovery
   * migrations, rollback, and backups
5. Identify existing behavior that could regress.
6. Define the required invariants, failure cases, and recovery behavior.
7. Determine whether the work should be divided into smaller commits or pull requests.

Do not begin with an isolated patch when the requested behavior crosses multiple architectural boundaries.

## Implementation requirements

Implement the complete production behavior, not only the most visible UI or primary call path.

When applicable:

* Enforce important rules at the repository or domain boundary, not only in the UI.
* Cover every writer and mutation entry point.
* Preserve deterministic behavior across devices and persistence stores.
* Do not silently guess when historical or duplicated data is ambiguous.
* Provide a deliberate user-accessible resolution path for recoverable ambiguity.
* Keep synchronization stores and local persistence consistent.
* Validate ownership and write permissions before destructive or synchronizing operations.
* Provide rollback, backup, or safe failure behavior for migrations and repairs.
* Maintain accessibility and scene-local behavior for presented UI.
* Preserve compatibility with existing persisted data.

## Testing requirements

Before presenting the change, add or update tests covering:

1. Normal behavior.
2. Boundary conditions.
3. Failure behavior.
4. Regression behavior.
5. Invalid or incomplete persisted state.
6. Every affected mutation or caller path.

Also add the following when applicable:

* concurrency and overlapping-operation tests
* actor-isolation tests
* cross-device determinism tests
* synchronization convergence tests
* owner and participant permission tests
* migration tests
* rollback and backup-failure tests
* process-restoration tests
* multi-window or multi-scene tests
* ambiguity-resolution tests
* accessibility behavior tests

Tests must validate resulting relationships and persisted state, not only counts, identifiers, or successful return values.

## Required verification

Run all repository-supported verification relevant to the change.

At minimum, run:

```sh
bash Scripts/verify-architecture.sh
bash Scripts/verify-concurrency.sh
```

Use the actual workspace or project, scheme, destination, and configuration defined by the repository. Do not invent successful results and do not claim a command was run when it was not.

When the repository provides additional lint, formatting, migration, integration, or architecture checks, run those as applicable.

## Required self-review

Before pushing a branch or opening or updating a pull request:

1. Inspect the entire resulting diff.
2. Review changed and unchanged surrounding code.
3. Trace every affected caller and mutation path again.
4. Perform an adversarial pull-request-style review.
5. Check specifically for:

   * data loss
   * stale references
   * synchronization divergence
   * bypassed mutation paths
   * race conditions
   * actor-isolation violations
   * nondeterministic behavior
   * permission failures
   * incomplete rollback
   * inaccessible recovery states
   * navigation or scene regressions
   * missing tests
6. Fix all material findings.
7. Re-run the relevant build and test commands.
8. Inspect the corrected full diff.
9. Perform a final review after all corrections.

GitHub review is an independent final check. It must not be used as the primary process for discovering unfinished implementation work.

## Pull-request and commit scope

Split work into smaller commits or pull requests when separate architectural foundations, migrations, UI workflows, or synchronization changes can be independently verified.

A large change should not be kept in one pull request merely because the user described it as one feature.

Each commit must represent a coherent and reviewable change. Avoid mixing unrelated cleanup with behavioral changes unless the cleanup is required for correctness.

## Completion requirements

Do not describe work as complete, return generated project files, push a final branch, or open a pull request until the required implementation, testing, verification, self-review, corrections, and final review have been completed.

If required verification cannot be performed:

* Mark the work as incomplete.
* State exactly what could not be verified.
* Explain why it could not be verified.
* Identify the remaining risk.
* Do not present assumptions as successful test results.

## Required delivery report

Every completed delivery must report:

### Behavior implemented

Describe the user-visible and system behavior that changed.

### Files changed

List every file added, modified, renamed, or deleted.

### Architecture and regression analysis

Describe:

* production call paths reviewed
* persistence and synchronization effects
* concurrency effects
* navigation, scene, UI, and accessibility effects
* existing features considered for regression

### Tests

List every test added or updated and the behavior it verifies.

### Verification

Provide the exact commands run and their results.

## Verification Cadence

Do not run full repository verification scripts during routine code inspection,
exploration, incremental edits, or after each individual fix.

During implementation:
- Use code inspection first.
- Run only narrowly targeted tests when needed to validate a specific change.
- Do not run Scripts/verify-concurrency.sh or other full verification suites
  after every edit or review finding.
- Batch related fixes together before verification.

Run the full required verification suite only at these checkpoints:
1. After the implementation and tests are substantially complete.
2. After the adversarial self-review, if that review causes material code changes.
3. Immediately before pushing/updating the PR, if the previous full verification
   is no longer valid because code changed.

Do not rerun an unchanged verification suite merely because additional code was
inspected or another review pass was performed.

For code-review-only tasks:
- Do not run local build/test/verification scripts unless reproducing a suspected
  defect requires them.
- Prefer inspecting the existing CI result for the exact PR head commit.

### Self-review findings

Report material issues found during internal review and how they were corrected.

Do not state that no findings existed unless the adversarial review was actually performed.

### Remaining risks

List any limitations, unverified behavior, unresolved risk, or follow-up work. State `None identified` only after completing the required review and verification.
