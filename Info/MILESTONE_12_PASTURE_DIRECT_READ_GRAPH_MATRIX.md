# Milestone 12 — Pasture and Pasture Group direct read-graph ownership

## Design before implementation

The selected-Herd Pasture repository scopes top-level fetches, but its direct summary/detail paths read `pasture.group` and count `pasture.animals` without checking their Herd owners. Group list uses `group.pastures.count` and Group Detail maps those members without validating membership ownership. Foreign-Herd objects linked through those Core Data relationships can therefore affect direct Pasture or Group projections even though the top-level result is Herd-scoped. The M9 Dashboard uses a separate Herd-constrained count query and already checks the linked group owner; PR #160 separately validates full Animal graphs for resident summaries.

**Design:** Add a shared Data-only validation helper near the existing Pasture projection for these inverse membership/count relationships. Validate selected-Herd group and linked resident ownership before mapping direct Pasture summary/detail; validate selected-Herd group memberships before count or nested detail mapping; reuse the same guarded projections for mutation return snapshots. Fail closed on corrupt reads without mutating/repairing; do not load an Animal's unrelated tag, health or history graph for a Pasture count. Keep existing query filters, deterministic ordering, transactions, Dashboard query performance, SwiftData legacy file handling, UI and schema intact.

**Ownership:** This PR owns direct Pasture/Group read-projection relationship ownership only. M4 owns group assignment/reorder and normal mutation contracts; M6 owns atomic deletion and rollback; PR #160 owns full Pasture resident Animal summaries and delete preflight; M9 owns Dashboard's distinct Herd-filtered count query; the earlier M12 Pasture ordering matrix owns tie-breaking. No new SwiftData work. Do not retire `CORE_DATA_CUTOVER.md` before the legacy-data release decision.
