# Milestone 12 — Dashboard/Home Working graph read parity

## Design before production edits

The direct `CoreDataWorkingRepository.fetchSessions`, `fetchSessionDetail`, and queue editor enforce `validateSessionGraph` before mapping selected-Herd sessions. This covers source-Pasture snapshot equality and ownership, queue-to-session and queue-to-Animal relationships, queue source/destination Pasture snapshots, treatment/health/pregnancy child session and Animal ownership, and active-Animal inverse session integrity. In contrast, the independently assembled `CoreDataReadModelActor.fetchDashboardRecords` calls `dashboardWorkingSessionRecord`, which only validates session/source Pasture Herd ownership and queue ID/Herd/session. A store may therefore show apparently healthy Dashboard/Home Working counts while direct Working reads reject the same active session.

Use the **existing** `CoreDataWorkingRepository.validateSessionGraph` as the single owner of Working relationship/snapshot validation from both read paths. Expose only this `nonisolated static` Data-layer validator to its sibling read actor. Keep the full-Herd ID-only session and queue preflights, 25-active-session window, `.current` query generation, sort, summary fields, queue mapping, and mutation/recovery/schema boundaries unchanged. Do not move the validator into Domain/Presentation or duplicate its rules. There are no writes or repairs.

The direct Working reader owns the graph invariant. This PR adds a second **production caller** for the same contract and a durable independent SQLite regression proving visible Dashboard/Home cannot disagree. Other rejected graph categories inherit that validator; the representative test uses a mismatched source-Pasture ID snapshot, including a valid unrelated session and legal independent-Herd data. It does not replicate the entire direct Working contract fixture matrix.
