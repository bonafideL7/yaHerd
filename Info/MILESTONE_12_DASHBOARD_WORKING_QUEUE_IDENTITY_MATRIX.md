# Milestone 12 — Dashboard active Working queue identity integrity

## Pre-edit design and ownership

The direct `CoreDataWorkingRepository` validates the complete selected-Herd `CDWorkingQueueItem` UUID cohort before returning Working session list/detail/editor. The independent M9 `CoreDataReadModelActor.fetchDashboardRecords` instead fetches up to 25 active Working sessions, checks the session UUID cohort, then `dashboardWorkingSessionRecord` validates queue UUIDs **within each session only**. Two physical queue rows with one application UUID in two displayed active sessions can therefore be counted and presented as separate entries on Dashboard and Home even though the direct Working repository rejects the same selected-Herd corruption.

Validate the combined `queueItems` relationships of **all fetched active sessions** once before mapping the summary records, reusing `CoreDataAnimalMutation.validateUniqueApplicationIDs` and the existing `CoreDataPersistenceError.duplicateApplicationID`. Retain each session's existing queue-ownership and session-relationship checks. This is a read-only, bounded-view reconciliation; do not increase the active session fetch limit, add a full-Herd queue fetch, alter the underlying M9 asynchronous query design, or touch Core Data schema, migration, mutations, SwiftData, UI, recovery or synchronization. A queue UUID reused by another Herd remains legal.

This slice deliberately validates the *displayed active-session cohort*, not all selected-Herd queue rows. Full-Herd read integrity is already owned by the direct Working repository and its contract (#166). The existing Dashboard active-session 25-row bound is owned by M9; the absence of full-Herd validation for undisplayed/inactive sessions remains a separate bounded-query tradeoff rather than a hidden assertion that this PR solves it.
