# Milestone 12 — Dashboard Pasture resident-count cohort

## Pre-edit design and contract boundaries

`CoreDataReadModelActor.dashboardPastureRecords` currently executes one `context.count(for:)` per selected-Herd Pasture. `fetchDashboardRecords` has already fetched *all* selected-Herd Animals in the same pinned query generation; standalone `fetchDashboardPastureRecords` instead runs N separate count queries. Preserve the exact predicate (same physical selected Herd, current Pasture, nonarchived, active raw status), selected-Herd Pasture/linked-Group ID validation, cross-Herd exclusion, sort, and zero count. Count by Core Data Pasture `objectID` **inside Data only**, never by display name or possibly-corrupt globally reused application UUID.

For the full Dashboard/Home aggregate, reuse its already-loaded Herd Animal cohort; for the standalone Pasture list, fetch one selected-Herd active/assigned Animal cohort with a batch hint and prefetched `currentPasture` relationship, then aggregate once. The result remains read-only and observes the caller's pinned `.current` generation. This removes N-per-Pasture count queries; it does not guarantee lower wall-clock latency or bounded total Core Data fault-array memory without a benchmark. Do not claim a SQLite grouped-aggregate query or introduce one without validating its supported Core Data result shape.
