# Milestone 12 — Working treatment-template list identity and ordering consistency

## Design before production edits

The direct Core Data template library `CoreDataWorkingTreatmentTemplateRepository.fetchTemplates` currently selects one Herd and sorts only by `name`. By contrast, `CoreDataReadModelActor.fetchHomeTreatmentTemplates(limit:)` already sorts `name` then persisted `id`, and rejects duplicate application UUIDs within its fetched selected-Herd cohort. Core Data does not guarantee which same-name physical row the library returns first; this can reorder distinct persisted options between independent contexts. If two selected-Herd templates physically share an application UUID, the direct list can return both as apparently valid while the Home query rejects the same cohort.

Keep the already-established Home sort contract (`name` ascending, `id` ascending) and reuse `CoreDataAnimalMutation.validateUniqueApplicationIDs` on the complete direct selected-Herd template array before mapping. Preserve the existing strict `WorkingMapper.treatmentTemplateItems` payload decoder. No new repository abstraction, custom comparator, schema, mutation, recovery, navigation, synchronization, SwiftData, UI or Home read-model change.

The direct list has no fetch limit; its complete selected-Herd UUID preflight therefore detects duplicates even when individual template detail lookups would already reject an ambiguous ID through `CoreDataLookup.herdOwned`. The bounded Home query retains its existing *bounded* validation contract; this change does not claim to validate IDs outside the Home request's fetched page. Ordinary template creation/update/delete, name uniqueness policy, session snapshot adoption and rollback remain with the M8 permanent contracts. Existing M12 strict template payload coverage remains authoritative for corrupt embedded treatment items.
