# Core Data sample herd — pre-implementation behavior matrix

## Design and scope

The previous Animal list empty state exposed **Add Sample Data** and **Add Large Sample Data** while a sample seeder was available. M11 removed the unused SwiftData writers and then the disabled UI/injection seam (#139, #144). Reintroduce the same entry point and labels, but through a new **Core Data-only**, selected-Herd-scoped, atomic writer. The large fixture deliberately contains hundreds of animals; both fixtures exercise all 18 native model entities and every major read projection. No SwiftData, demo store, automatic startup seeding, migrations, additional persistence graph, user-data replacement, or permanent CI changes.

The seed is opt-in and empty-Herd-only; both the display-time availability preflight and the write-context guard check the same complete selected-Herd Animal, Pasture, **PastureGroup**, Field Check and Working cohorts. Visibility additionally requires Animal-list loading to finish. Reject an existing graph without modifying it; re-check in the write transaction. Existing Core Data Tag Color rows may preexist and are reused. Reserve built-in Tag Color materialization through the existing Core Data coordinator and participate in the existing animal/pasture write boundaries so another scene cannot race into duplicate stable UUID colors. Construct all required managed-object attributes, valid raw enum values, Herd ownership, snapshots and inverse relationships **before a single transaction save**. Failure rolls back the entire sample; read-only recovery refuses writes. Publish one existing all-feature Animal mutation after successful commit, then refresh the Animal list. Keep editing, filtering, regular Add Animal, other features and empty-state recovery buttons unchanged. Explicit user action is the sole trigger.

The sample fixture's advertised cow/heifer distribution must match production's maternal-offspring classifier (including older offspring where there are fewer calves than cows). Every finished Working queue must preserve a nonnil destination pasture relation and ID/name snapshot, consistent with the real completion path; active session queue rows can remain without a destination. Distinct review findings are owned by the already represented seed-writing and empty-state row categories, not a new duplicate test infrastructure.

**Ownership:** This PR owns Core Data sample fixture composition, original empty-state UI and application injection. M3 owns executor rollback and Core Data store; M4–M8 own native feature write and graph invariants; M9/M12 own read projections; M10 owns selected-Herd bootstrap/recovery. Do not duplicate their permanent contracts, or weaken them to permit synthetic data.

## Review reconciliation — standalone pasture-group lifecycle

The Pasture feature permits a `PastureGroup` with zero assigned `Pasture` records; its creation is an independent user-write path (`PastureFeatureDependencies.groupEditorRepository.createGroup`). The Animal list's list/pasture-option loading does not reveal such a group, so **both** the UI availability preflight and the transactional predicate must treat a selected-Herd standalone group as nonempty. Creating the three synthetic groups without this check could duplicate an existing "North Rotation" name and violate user-record preservation. The existing app graph non-destructive guard contract now exercises (1) group-only state (no pastures/animals), (2) a group plus one pasture, (3) identical group ID/name/membership after both rejected compact and large seed attempts, (4) absence of injected Animal and Working records, and (5) no mutation publication from either failed seed. No new top-level category is necessary: this is a missing lifecycle state of the existing "Preserve safety and compatibility at the empty-state UI and app boundary" row, with matching compact/large no-op and unrelated-record dimensions.
