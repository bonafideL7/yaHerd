# Milestone 12 — stable Core Data pasture-read ordering

## Design and boundaries

Core Data relationship sets and fetches are not ordered when all declared sort keys tie. `CoreDataPastureRepository.fetchResidentAnimals` currently compares display tags only; multiple untagged residents have the same key, so the resident list can change order on refresh or SQLite reopen. Pasture and group list/read paths similarly lack a final persisted-identity tie-break when sort-order and name comparisons tie (including values that compare equal under `localizedStandardCompare`).

Preserve existing first-order semantics, adding the already-persisted application UUID ascending as the **last** comparison. Do not reassign identities, change pasture sort order, rename, mutate tags, change group memberships, alter active-count semantics, introduce a new index/model, or change independent Dashboard/M9 read models. Reuse the existing read paths. `fetchPastures` must continue honoring stored `sortOrder` before name; `fetchPastureOptions` and `fetchPastureGroups` stay name-first; resident reads stay display-tag-first; group-detail membership stays sortOrder-first. The same tie-break applies to `reorder`'s remaining-pasture fallback so a partial reorder is stable when preexisting persisted sortOrder/name keys tie.

Production-reader trace: `PastureDetailViewModel` consumes resident summaries; `PastureTileListViewModel`, `PastureTilePickerViewModel`, and `PastureGroupDetailViewModel` consume pasture summaries; `PasturePickerView`, `AnimalListViewModel`/editor option use cases, Field Check setup, and Working setup/finish flows consume pasture options; `PastureGroupListViewModel` consumes groups; `PastureGroupDetailViewModel` consumes group detail. Pasture deletion planning consumes residents, but only their membership/IDs matter to that transaction, not presentation order. The App mutation-publishing/coordinating wrappers forward the same repository contract.
