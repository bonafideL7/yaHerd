# Accessible custom control contrast — behavioral coverage matrix

## Review context and design

The first version of PR #196 introduced the shared foreground modifier before this matrix was committed. The review identified that omission; this document inventories the existing implementation and affected production paths retrospectively, and serves as the current coverage record before further scope changes.

**Problem:** The app's asset accent is dark burgundy in Light Mode and pale green in Dark Mode. Fixed white on the Dark Mode accent has about **1.56:1** contrast; black on the same fill has about **13.43:1**. White can also be unreadable on bright status colors such as yellow.

**Smallest design:** Distinguish semantic accent-backed controls, colored icon badges, and tinted text on neutral cards. Do not feed `Color.accentColor` through UIKit's SwiftUI-to-UIColor bridge to guess which asset appearance is drawn. Apply the shared `View.readableForeground(on:)` modifier only to text or symbols on **opaque solid color fills**, using resolved light/dark `UIColor` components and WCAG relative luminance to choose black or white. Both are compared mathematically; the better option on an opaque sRGB fill always reaches at least 4.5:1. Keep the defined app accent asset unchanged; colored icon-badge fills may be darkened just enough for a white glyph to meet contrast. Preserve shapes, sizes, actions, and custom disabled/read-only gates. SwiftUI's native button styles and tinted glass/material backgrounds stay responsible for their own composited foregrounds.

**Boundaries:** Rendering, Pasture Checks overview layout, and context-appropriate accessory visibility only. No Core Data, mutation, synchronization, migration, concurrent read logic, field-check workflow state, route mutation, persistent state, or scene restoration changes. Recovery *presentation* changes, not recovery behavior. A system appearance switch causes a new body evaluation; no extra app state or persistence should be introduced. Alpha/composited glass backgrounds do **not** meet the opaque-color assumption. Unresolvable non-RGB colors use SwiftUI's `.primary` fallback instead of inventing a contrast ratio.


> **PR #198 data projection update:** this matrix retains ownership of the compact overview layout, semantic contrast, filter capsule styling and button behavior. The count/section behavior previously described as Recent was replaced by Completed with complete history. `Info/PASTURE_CHECKS_ALL_HISTORY_MATRIX.md` owns the updated data/ordering/identity contract; PR #196 visual tests and ownership remain unchanged.

## Final semantic appearance rules (Light and Dark)

- **Brand accent control:** Background remains the named `AccentColor` asset (Light burgundy / Dark pale green); foreground is **white in Light Mode / black in Dark Mode**. Used for selected field-check filters, floating creation controls and prominent actions. Tests read the named asset rather than attempting to infer its appearance from the SwiftUI-to-UIKit bridge.
- **Colored icon badges:** A shared `readableIconBadge` modifier retains the original status hue but darkens bright fills only when necessary to guarantee a **white** icon at ≥4.5:1. Applies to Home summary/action/operational rows, suggestions, and Dashboard metric/lifecycle circles. Black symbols on saturated Light Mode badges are no longer part of the visual scheme.
- **Tinted link text on grouped cards:** The `readableCardTextTint` rule compares tint to the actual secondary grouped card surface in the selected appearance and adjusts tint toward a readable value when necessary (≥4.5:1).
- **System-controlled native glass and toolbars:** Do not force a background-derived label foreground without knowing the composited fill; existing separate native style handling remains. Device rendering, disabled-state compositing, and dynamic increased-contrast settings remain unverified.
