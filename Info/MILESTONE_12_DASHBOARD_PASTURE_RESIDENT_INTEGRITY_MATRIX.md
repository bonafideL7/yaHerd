# Milestone 12 — Dashboard Pasture resident identity and Herd-ownership integrity

## Pre-edit design, read boundaries, and failure

The full Dashboard materializes the complete selected-Herd Animal cohort and rejects duplicate Animal application UUIDs before projecting the Pasture summary. The independent `fetchDashboardPastureRecords` only validates Pasture and referenced Group UUIDs; even though #180 now fetches a selected-Herd active resident cohort, it can return apparently healthy Pasture counts when an archived/off-predicate physical Animal duplicates an active Animal UUID. This is an independently displayed read projection that disagrees with the full Dashboard and direct Animal library. Reuse the already-bounded selected-Herd ID-only preflight in the standalone read, before fetching Pasture data. Do not add the preflight to the full Dashboard because it already validates the fetched complete Animal cohort.

Direct `CoreDataPastureRepository.validatePastureReadGraph` validates **every** inverse `pasture.animals` member's Herd, even an inactive or archived resident. Both Dashboard Pasture read paths (#180) instead count only active selected-Herd Animals using their forward `currentPasture` relationship. A physically foreign-Herd Animal attached to a selected-Herd Pasture is silently omitted, while direct Pasture summary/detail and Group detail throw `invalidHerdOwnership`. Add one ID-limited read-only inverse-ownership probe by `currentPasture.herd == selectedHerd && herd != selectedHerd` in the shared Dashboard Pasture projection, before count mapping. Throw the existing typed Animal ownership error, including physical stored Animal UUID and actual Herd. The separate selected-Herd Animal -> foreign-Pasture relationship validation remains owned by the complete Animal graph/direct Animal reader; this PR does not replace those graph contracts.

The existing `.current` pinned query generation in both Dashboard entry points already covers these preflights and all projections. Preserve #180's cohort-based active count, physical Pasture `NSManagedObjectID` bucketing, original sort, Group validation, zero counts, and one resident cohort fetch rather than restoring per-Pasture COUNT fanout. No mutation, repair, schema, UI, sync, SwiftData, migration, or Core Data query infrastructure changes.
