# Milestone 11 — Freeze the Legacy Persistence Boundary

## Design and scope

The M10 cutover runs the whole app on Core Data, and M11 PRs #127–#140 removed the unused SwiftData runtime repositories, assemblies, mappers and extensions. The remaining archived SwiftData model declarations, `YaHerdSchemaV1`, its aliases and treatment vocabulary are retained pending an explicit existing-user lossless upgrade decision. The existing 16 `@Model` source files, schema, current-model aliases and treatment terminology alias are pinned by their original Git blob identities (19 files total), so modifying or expanding declarations within an existing allowed file fails without an intentional manifest update. This is a **static architecture safeguard**: it does not convert legacy stores or delete model declarations.

Before editing verification code, inspected `yaHerdApp`, `CoreDataAppPersistenceAssembly`, `CoreDataLegacyStorePreflight`, the Core Data app-graph tests, `Scripts/verify-core-data.sh`, the surviving model/schema paths, and the existing architecture checker. The existing Core Data verifier only rejects `import SwiftData` in three specific Core Data directories; it cannot reject a newly added dependency in App/Presentation/other Data directories. The earlier M11 guard and the pre-existing Domain import rule recognized only bare imports (or an optional `@preconcurrency` for M11). This left valid attributed imports such as `@_implementationOnly import SwiftData` and `@_exported import CloudKit` unrecognized. The corrective design uses one module-extraction pattern for import declarations, including repeated attributes, attribute arguments, Swift 6 access-level modifiers (`private`, `fileprivate`, `internal`, `package`, `public`, `open`), and symbol-qualified imports. A follow-up review found that the previous parser missed access-level imports in both the persistence guard and its sibling Domain boundary; the same module parser must handle modifiers alone or combined with attributes rather than adding a separate special-case regex. The Domain Foundation-only boundary shares this correction. The first GitHub verification run at `cc892f8` exposed a separate parser bootstrap failure: the added regex has unbalanced grouping (`re.PatternError` at offset 103). This is an architecture-check execution failure, not a Core Data behavior regression. Correct the shared expression rather than weakening either policy, and require the checker to compile and run before claiming the static rules are verified.

**This PR owns:** the repository-wide static SwiftData import/API, legacy direct-schema-reference and CloudKit regression guard, a shared attributed/access-modified import parser for that guard and the existing Domain import rule, and exact archived-declaration content pinning in `Scripts/verify-architecture.sh`. **Other owners:** M10 Core Data graph/preflight/recovery, M4–M9 repository contracts, and a separate lossless existing-user conversion/release decision. No active repository, presentation behavior, schema, migration mechanism, tests, Xcode target settings, startup, or persisted data changes.

No verification, test, lint, build or CI command is run under `AGENTS.md` absent explicit user instruction.

## Static inspection and release boundary

- Legacy allowance requires **both exact file paths and original Git blob hashes** rather than `yaHerd/Data/Models/**` wildcard. Each of the 19 retained files is byte-for-byte frozen, including its model declarations, relationship properties, versioned schema, aliases and compatibility names. A new declaration, changed field, removed file, or even added import within an allowed source fails unless the manifest is intentionally revised in a separate reviewed change.
- Shared import recognition handles bare imports, imports with arbitrary Swift attributes (including argument-bearing `_spi` attributes), access-level modifiers (`private`, `fileprivate`, `internal`, `package`, `public`, `open`), mixed attribute/access prefixes, and symbol-qualified imports. This is applied to the M11 `SwiftData`/`CloudKit` checks **and** the existing Domain Foundation-only check so either attribute or modifier prefixes cannot bypass those rules. The concrete review paths are `private import SwiftData`, `internal import CloudKit` and `package import SwiftUI` in Domain; allowed `private import Foundation` remains accepted in Domain. New `SwiftData` or `CloudKit` imports anywhere else fail; legacy schema references outside frozen model/schema files fail. `@Query`, `@ModelActor` and all SwiftData container/context APIs are forbidden across all production sources. Existing `@Model` and `VersionedSchema` declarations are tolerated only within the pinned files. Source scanning is repository-wide and future-file-inclusive.
- Old `YaHerdSchemaV1`, `YaHerdCurrentModels`, `WorkingTreatmentTerminologyCompatibility`, preflight, recovery and archive/export remain in place. Existing users cannot yet be automatically upgraded from their old SwiftData files; this remains a release blocker.
- The earlier run of GitHub verification at `cc892f8` failed because Python could not compile the shared `swift_import` regex (unbalanced parenthesis). The correction must preserve all six import-prefix categories and the 19 pinned archived files, and the architecture checker must actually reach its rules. Under the current explicit user request, relevant verification execution is authorized; record the new execution evidence rather than asserting a pass from inspection alone.
