# Milestone 3 Core Data Persistence Foundation Matrix

This matrix covers the production Core Data infrastructure introduced by Milestone 3. The app continues to run on SwiftData until the decisive AppDependencies cutover; feature repositories remain owned by later milestones.

| Production operation / behavior | Production callers | Success path | Error / rollback path | Clear / reset behavior | Batch / mixed-input behavior | Same-context behavior | Fresh-context reload | Production read projections | Relationships / history | Cross-feature effects | Unrelated control records | Identity / metadata | Contract owner |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Load the final local Core Data persistent container | None: production AppDependencies still use SwiftData until Milestone 10; Milestone 3 exposes the final Core Data container for repository/harness use only | Covered: `CoreDataPersistentContainer.load` loads `yaHerdModel` into one local SQLite store, with an in-memory option only for isolated tests | Covered: model/store loading failures are surfaced as `CoreDataPersistenceError` rather than silently falling back to SwiftData or another store | N/A: this milestone does not delete/reset a production store; development SwiftData migration/reset is intentionally absent | N/A: persistent-store loading is one container-level operation | Covered: `CoreDataPersistentContainer` encapsulates the raw `NSPersistentContainer` and does not expose or rely on its view context; repository-facing access is limited to coordinator-backed private contexts | Covered: harness opens a new context over the loaded store and observes committed records | Delegated: feature read projections are implemented by Milestones 4–9 | Covered: the container loads the Milestone 2 relationship graph unchanged | Covered: every later Core Data feature repository shares this one local graph | Covered: load failure does not switch to or mutate the existing SwiftData runtime | Covered: no CloudKit/iCloud/shared-store identifiers are introduced; application UUID remains model identity | This PR |
| Create queue-confined Core Data read and write contexts | None: no production Core Data repository exists yet; contexts are consumed by the Milestone 3 harness and future repositories | Covered: `CoreDataContextFactory` exposes only private-queue read/write contexts created by the persistence wrapper and attached to the same coordinator; the raw container/view context are not part of the persistence API | Covered: callers receive Core Data errors rather than contexts silently changing stores or ownership | N/A: disposable contexts are discarded after use; no app-level reset behavior is introduced | Covered: each caller can create independent contexts without sharing staged state | Covered: context work is executed through asynchronous Core Data queue confinement; callers do not block the main actor while waiting for private-context work | Covered: independently created contexts re-fetch durable state from the shared coordinator/store | Delegated: projection/query policy belongs to repository/read-model milestones | Covered: all contexts operate on the same managed-object model and relationship graph | Covered: prevents feature implementations from inheriting SwiftData main-actor persistence constraints | Covered: one context's unsaved state is not visible through a fresh sibling context | Covered: contexts never expose `NSManagedObjectID` as application identity | This PR |
| Execute one logical write transaction with one final save | None: feature transaction writers begin in Milestones 4–8; the foundation harness exercises the executor directly | Covered: `CoreDataTransactionExecutor.performWrite` is `async`, executes `@Sendable` work with `NSManagedObjectContext.perform`, requires any returned value to be `Sendable`, and saves once only when changes exist; it never synchronously waits on the caller thread | Covered: any thrown mutation/save error rolls the transaction context back before propagating an explicit persistence error; failed one-shot contexts are discarded | N/A: feature-specific clear/reset semantics belong to repository contracts | Covered: a transaction block can stage multiple inserts/updates/deletes and commits them as one save boundary | Covered: successful results reflect the staged transaction; failed staged state is rolled back before the context is discarded | Covered: harness confirms committed records reload and failed records do not appear in a fresh context | Delegated: mutation-driven feature projections remain permanent repository/transaction contract ownership | Covered: relationship changes staged in the same block share the same atomic save boundary | Covered: provides the asynchronous atomic primitive used later by Animal, Pasture, Field Check, Working, Health and reference repositories; their Domain mutation contracts must become async when each Core Data implementation is introduced rather than adding synchronous waits | Covered: rollback test retains a pre-existing control record while rejecting staged failure state | Covered: application UUID values assigned by callers survive commit unchanged; executor does not mint identity | This PR for transaction mechanics; permanent transaction contracts own feature semantics |
| Resolve store-global Herd identity deterministically by application UUID | None: Core Data Herd repository is Milestone 4; Milestone 3 harness exercises the lookup primitive | Covered: `CoreDataLookup.herd(id:in:)` fetches by application UUID rather than fetch order or `NSManagedObjectID` | Covered: more than one matching Herd surfaces duplicate-identity failure; missing Herd returns nil for callers to interpret under their repository contract | N/A: current-Herd selection/reset is application state and remains Milestone 4+/App ownership | N/A: lookup resolves one application UUID at a time | Covered: lookup sees context-local committed/fetched state according to normal Core Data semantics | Covered: fresh context resolves the same Herd UUID after save/reload | Delegated: Herd summaries/current-Herd projections belong to `HerdRepositoryContract` and Milestone 4 | Covered: Herd is the root relationship target for all herd-owned records | Covered: this primitive is shared by every herd-scoped future repository | Covered: lookup does not mutate sibling Herd graphs | Covered: Herd identity is store-global and duplicate matches are treated as integrity failure | This PR for lookup mechanics; `IdentityContract` / `HerdRepositoryContract` own repository behavior |
| Resolve herd-owned identity by application UUID inside an explicit Herd scope | None: herd-scoped Core Data repositories begin in Milestone 4; Milestone 3 harness exercises the lookup primitive | Covered: `CoreDataLookup.herdOwned` first resolves the store-global Herd root through `herd(id:in:)` so duplicate Herd UUID corruption cannot select an arbitrary graph, then constrains the child fetch to that exact Herd object plus entity UUID; the same herd-owned application UUID may still exist in different valid Herd scopes | Covered: duplicate Herd roots fail before child lookup; duplicate child matches inside one validated Herd scope surface explicit duplicate-identity failure; a missing Herd or missing target returns nil | N/A: changing selected/current Herd is outside this low-level lookup | Covered: harness creates the same herd-owned UUID in two Herds and resolves each independently | Covered: lookup can resolve staged/committed objects only in the supplied context and scope | Covered: fresh contexts resolve each scoped record to the correct Herd after reload | Delegated: feature-specific projections remain their permanent contract owners | Covered: lookup follows the required Herd relationship from a uniquely resolved Herd root rather than resolving children through an ambiguous `herd.id` predicate or duplicating a Herd UUID field on each object | Covered: establishes one deterministic scoping primitive for Pasture, Animal, Field Check, Working, Health and reference-data repositories | Covered: resolving Herd A does not return or mutate Herd B's same-UUID record, and duplicate store-global Herd roots prevent all herd-owned lookup in that corrupted scope | Covered: herd-owned UUID identity is `Herd + UUID`; native Core Data object IDs remain internal | This PR for lookup mechanics; `IdentityContract` owns duplicate/scoping behavior |
| Support read-only store access without introducing a second business graph | None: the running app remains on SwiftData until Milestone 10; this PR exposes only generic Core Data read-only store access with no recovery-feature caller | Covered: the container can be opened with a read-only persistent-store description against the same local store; no feature-specific recovery policy is embedded in Data | Covered: read-only store-load failure is surfaced explicitly; writes attempted through a read-only assembly are rejected before transaction execution | Covered: callers can construct a normal read-write assembly against the same store after read-only access ends; no fallback or secondary business store is created | N/A: read-only access mode is container-wide | Covered: read-only policy is enforced before creating write transactions | Covered: read-only contexts use the same durable local store and therefore the same saved UUID/Herd graph | Delegated: Mapping application recovery mode to read-only Core Data access remains Milestone 10 cutover work | Covered: generic read-only access adds no snapshot import/export or mirror relationships | Covered: read-only access reuses the same Core Data store and cannot become a second persistence architecture or dual-write path | Covered: read-only access cannot create replacement business records through the transaction executor | Covered: store URL and application UUID identity are unchanged between read-write and recovery access | This PR for generic Core Data read-only access; application recovery policy/wiring delegated to Milestone 10 |
| Keep Core Data mapping inside the existing Data mapper boundary | None: feature Core Data repositories/mappers begin in Milestones 4–9; Milestone 3 establishes the mapping convention only | Covered: `Info/CORE_DATA_CUTOVER.md` now requires Core Data repositories to use the existing feature mapper types in `Data/Mappers` rather than a parallel `CoreData*Mapper` family, and managed objects are mapped before results leave Data | Delegated: invalid persisted payload decoding and feature-specific mapping failures belong to the corresponding repository/mapper milestone | N/A: mapping convention does not define feature clear/reset semantics | N/A: batch mapping behavior belongs to each feature repository/read-model implementation | Covered: managed objects are intended to be mapped on their owning context queue before Domain values are returned | Delegated: fresh-context Domain projection correctness is exercised by the corresponding permanent repository contracts as each Core Data repository is implemented | Delegated: Animal/Pasture/Field Check/Working/Home/Dashboard projection content remains owned by Milestones 4–9 and their permanent contracts | Delegated: relationship/history projection details remain feature-contract ownership | Covered: one mapper boundary prevents persistence technology from fragmenting Domain mapping across features | N/A: this convention itself performs no mutation of control records | Covered: application UUIDs may cross into Domain; `NSManagedObjectID`, contexts, managed objects, and store identifiers remain Data-only | This PR for mapping convention; concrete mapper implementations delegated to Milestones 4–9 |
