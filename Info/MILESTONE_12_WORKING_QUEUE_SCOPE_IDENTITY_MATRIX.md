# Milestone 12 — Selected-Herd Working Queue Identity Read Contract

## Finding and design

`CoreDataWorkingRepository.validateSessionGraph` checks application UUID uniqueness for queue rows **within each Working session**. The selected-Herd session-list reader checks session UUIDs but not a complete Herd's queue UUIDs. Two distinct physical queue items in different sessions can consequently share one application UUID: session list/detail emit ambiguous queue identities while `CoreDataLookup.herdOwned(CDWorkingQueueItem.self, id:)`, used by queue editor and queue mutation paths, correctly fails closed.

Validate the **complete selected-Herd queue cohort once per direct read operation** before mapping any Working session or queue editor. Reuse `CoreDataAnimalMutation.validateUniqueApplicationIDs` and its typed `CoreDataPersistenceError.duplicateApplicationID`; do not deduplicate, choose a winner, generate replacement IDs, or mutate the store. A queue UUID may legitimately appear in another Herd because its identity scope is the owning Herd. Keep validation outside `validateSessionGraph` to avoid a full-Herd fetch for every row of the session list. Preserve the existing session-specific ownership/relationship validator, mapped snapshot shape and ordering.

This PR owns direct Working list/detail/editor **read integrity for queue UUIDs across sessions** and an independent SQLite/read-only reload regression. M8 owns normal Working mutation, historical snapshots, rollback and session lifecycle, including queue mutation lookup; M9 owns bounded Dashboard/Home projections; M3/M12 foundation contracts own generic `CoreDataLookup` ambiguity and cross-Herd semantics. Other Working child entity identities (treatment/health/pregnancy) remain with their established M5/M8 graph and direct lookup contracts; they are not queue UI identities emitted by the session list/detail. No schema, migration, legacy SwiftData, CloudKit, UI/navigation, automatic data repair or new generic validation infrastructure.
