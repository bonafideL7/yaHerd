# Milestone 12 — asynchronous Dashboard linked-Group identity consistency

## Design before production edits

The direct `CoreDataPastureRepository.fetchPastures` and `fetchPastureDetail` now reject duplicate physical `CDPastureGroup.id` values within the selected Herd when projecting a linked Group. The independent M9 `CoreDataReadModelActor.dashboardPastureRecords` already checks duplicate Pasture IDs and the actual owning Herd of a linked Group, but projects `group.restDays` without checking the related selected-Herd Group UUID cohort. Thus Dashboard and Home can return plausible but ambiguous group-derived rest-days while their direct Pasture list/detail reject the same store.

Keep Dashboard's existing selected-Herd Pasture fetch and Herd-constrained active-Animal count. Before projecting any linked Group, fetch the complete **selected-Herd Group cohort in the same read context** and reuse `CoreDataAnimalMutation.validateUniqueApplicationIDs` once. As in the direct repository, skip the additional Group query when no Pasture links to a Group; do not validate unrelated Groups in that case. Detect equal Group IDs in the same Herd only; a different Herd may reuse the UUID. Reject the entire projection with the existing typed `CoreDataPersistenceError.duplicateApplicationID` before constructing any result. Never rekey, merge, rewrite or repair physical records.

This PR changes one existing M9 projection helper used by both `fetchDashboardRecords` and `fetchDashboardPastureRecords`; no new abstraction, changes to ordering, Core Data model/schema, mutation, UI, asynchronous execution, SwiftData, recovery, or Working/Home bounded query contracts. Performance remains one additional complete selected-Herd Group fetch only on linked-Pasture reads; its large-Herd cost remains unmeasured until verification is explicitly authorized.
