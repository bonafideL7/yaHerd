# Milestone 12 — Field Check Direct-Read Graph Integrity Matrix

## Scope and design (recorded before production changes)

The direct `CoreDataFieldCheckRepository` reads already reject duplicate application UUIDs for the selected Herd, but their session-summary/detail mappers traverse inverse child collections without checking whether a roster check or finding's own `herd` agrees with the selected session. Likewise `fetchOpenFindings` fetches by finding Herd while the finding snapshot reads `finding.session.id`, without checking session ownership. A malformed persisted relationship can therefore disclose a foreign-Herd child in a selected-Herd detail, or project a finding with a foreign session. App-level selection normally uses one Herd; multi-Herd fixtures here deliberately exercise persistence isolation and corrupt-graph rejection, not new multi-Herd behavior.

**This PR owns:** integrity validation immediately before the direct Field Check list/detail/open-finding read projections, including both relationship directions (selected session → child and selected child → session) and fresh-context regressions in `CoreDataFieldCheckRepositoryContractTests`. Reuse the existing Data-layer `CoreDataReadModelError.invalidHerdOwnership` and `invalidSessionRelationship`, instead of introducing another error/validator framework. Preserve all stored records unchanged on failed reads.

**Existing permanent owners:** M7 Field Check contract owns legal session/roster/finding writes, historical snapshots, locking, and rollback; M9 `CoreDataReadModelActor.validateFieldCheckWarningGraph` and `validateFindingRelationship` own the Home warning aggregate only; M3/M4 own physical SQLite identity and Herd bootstrap; M12 physical-delete contracts own deletion rules. This PR does not alter those contracts, the Core Data schema, mutation pathways, navigation, or SwiftData. Explicitly do not introduce background verification: `AGENTS.md` forbids running tests, build, lint, scripts, or CI without a request.

## Animal-specific read projection trace

`FieldCheckAnimalDetailView`'s initial `.task` load, `.refreshable` callback, Add Offspring dismissal, and post-mutation refresh flows invoke `FieldCheckAnimalDetailViewModel.load` / `refresh`. Those methods fetch `AnimalDetailSnapshot` through `AnimalDetailRepository` and the same complete `FieldCheckSessionDetailSnapshot` through `FieldCheckAnimalDetailRepository.fetchSessionDetail`. The view model's `animalCheck` chooses the roster entry for `animalDetail.id`; `animalFindings` filters the session findings by that same `animalID` and sorts descending by `recordedAt`. `FieldCheckAnimalDetailView` renders those projections under Check Status and Findings. The repository's Herd/session graph check occurs **before returning the entire session snapshot**, therefore a foreign-Herd roster entry or finding aborts both ordinary session detail and animal-specific detail, rather than slipping through an animal-ID filter. The view model catches and reports failed reads; its previous cached state on refresh failure is existing Presentation lifecycle behavior, outside the read-graph integrity change. It does not receive any partially mapped invalid snapshot.

This is another consumer of the **same validation boundary**, not a separate physical read, mapper or integrity rule. The existing direct session-detail Core Data regression tests cover rejection before any consumer can filter; `FieldCheckSessionDetailViewModelTests.testAnimalDetailActionsExecuteInInvocationOrder` owns the existing animal-detail post-mutation refresh orchestration. No second duplicated persistence suite or UI implementation is introduced.

## Dashboard Field Check projections and failure-path trace

`DashboardView` is another **production consumer of the direct session-summary boundary**, not the M9 `HomeFieldCheckQueryReading` warning aggregate. `CoreDataAppPersistenceAssembly` provides the mutation-publishing `CoreDataFieldCheckRepository` as `homeDependencies.fieldCheckOverviewReader`. `DashboardView` creates a separate `FieldChecksViewModel`, calls its `observe(using:mutationStream:)` from `.task` (including Field Check revision reloads), and calls `load(using:)` on Dashboard pull-to-refresh. The same `fetchSessions` validation runs before the Dashboard's session array can be updated with an invalid session summary. The view also loads a separate `DashboardQueryReading` snapshot for its non-Field-Check charts; this PR does not change that path.

`DashboardPresentationData(snapshot:fieldCheckSessions:)` receives `fieldChecksModel.sessions`. It sorts those sessions by `startedAt`, takes the most recent twelve and derives `fieldCheckHistoryValues` (session ID, label, date, expected head count, counted head, flagged, missing, and open findings). `DashboardChartsContent.fieldCheckTrendChart` charts expected versus counted head count from these values; `fieldCheckOutcomesChart` charts the flagged, missing, and open-finding counts from `fieldCheckOutcomeValues`. Both use the **same validated session summaries**. Dashboard's `FieldChecksViewModel.load` **also executes** `fetchOpenFindings` after `fetchSessions`, but `DashboardPresentationData` reads only `fieldChecksModel.sessions`; it never reads `fieldChecksModel.openFindings`. Therefore the finding query's failure can trigger the Dashboard alert without supplying data to either Dashboard Field Check chart.

On a corrupt selected-session child graph, `fetchSessions` throws before returning any summary. `FieldChecksViewModel.load` catches the error and retains its previous `sessions`; `DashboardView` displays the shared `Dashboard Error` alert via `fieldChecksModel.errorMessage`. At first load the Field Check charts are empty; after an unsuccessful reload they continue showing previously loaded session values, **not newly projected corrupt values**. If `fetchSessions` succeeds but the subsequent `fetchOpenFindings` query fails, the valid session summary array has already been assigned and the same error alert is shown; the charts remain derived only from valid summaries. Existing chart ordering, empty-state presentation, cached-state semantics and mutation observation are preserved, not reimplemented here.

The direct repository contract tests in this PR protect the shared boundary for `FieldChecksView` and both Dashboard charts. `DashboardPresentationDataTests` and the existing Dashboard chart implementations own presentation transformations; no duplicate UI fixture or chart-test suite is necessary for this integrity-only change. Tests and verification were not run per `AGENTS.md`.
