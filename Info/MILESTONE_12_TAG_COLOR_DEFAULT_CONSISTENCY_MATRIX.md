# Milestone 12 — Tag Color deterministic default recovery and library ordering

## Design and affected paths

The physical Core Data Tag Color library can contain multiple persisted `isDefault` flags after a failed/partial external repair, imported or manually modified store, or earlier inconsistent records. The normal explicit `setDefaultColor` write is exclusive. However, the current **read** chooses the first default in sortOrder/name order, while `upsert` and `deleteColors` normalization choose the newest `updatedAt` and then `sortOrder`, with no final tie-break. `restoreDefaultColors` and `reorder` choose first from the fetched physical collection. A passive fetch can therefore present one default that a subsequent healing mutation silently replaces with another. Both Tag Color snapshot sorting and repair selection can be nondeterministic on equal keys.

Make the existing normalization precedence authoritative everywhere: newest `updatedAt`, then smallest `sortOrder`, then localized name comparison, then persisted UUID ascending. Use **one snapshot-based selection helper** for passive reads and a captured pre-mutation default ID for writes that can change comparison metadata before normalizing. Reorder must preserve the pre-write winner even if it changes a losing record's sortOrder/updatedAt; an edit of the losing default and canonical restoration have the same hazard. An explicit incoming upsert default request (or direct setDefaultColor) overrides the pre-write winner. Deleted, hidden or remapped winners may legitimately fall back to the remaining visible default. Do not change ordinary explicit default selection or automatically repair physical data on read. Keep library display order sortOrder/name/UUID, preserving existing display precedence. Do not change tags, physical schema, Herd scope, canonical IDs, transaction/rollback boundaries, reference remapping, or independent color read projections in Animal/Field Check/Working. The one projected default should remain the same before and after an unrelated successful healing operation; a passive fetch must remain read-only.

Production callers traced: `TagColorLibraryStore` reads `fetchColors` for settings, picker and default tag color; `MutationPublishingTagColorRepository` wraps `setDefaultColor`, `upsert`, `deleteColors`, `reorder`, `restoreDefaultColors`; `CoreDataTagColorRepository.fetchColor(id:)` and the seven physical AnimalTag/Field Check/Working color references use unchanged per-ID semantics. `CoreDataReadModelActor` and Domain tag formatting do not choose the library default.

## Final static reconciliation

- The changed source paths are limited to `CoreDataTagColorRepository.swift`; passive reads use `preferredDefaultID(in:)`. Mutations capture that ID **before** changing comparison metadata and pass it to `normalizeDefaults` where appropriate, preventing reorder/upsert/restore from choosing a different winner solely because a losing row's `updatedAt` or `sortOrder` changed.
- `fetchColors` still returns synthesized virtual built-ins without writing; hidden physical definitions are excluded by `fetchPersistedColors`. Repair prefers a visible flagged default over a hidden flagged one, matching the visible library.
- `snapshotSort` retains sortOrder/name precedence and uses persisted UUID only for equal localized-name comparisons; no stored positions are rewritten during a passive fetch.
- `setDefaultColor(id:)` remains an explicit exclusive write and `fetchColor(id:)` remains a direct physical lookup; neither uses the preferred-default comparator.
- Existing suite is expanded with adversarial reorder of the physically flagged loser, edit of the losing default, and canonical restore of a nonpreferred flagged built-in. Other tests seed conflicting flags, assert `TagColorLibraryStore.defaultColorID`, use independent read-only SQLite assemblies, protect control definitions, and cover explicit override.
- No Domain port, Core Data model, managed relationship, transaction coordinator, field-check/working/animal projection, SwiftData archive or cutover/recovery path changed.
- Static diff and matrix review completed; **no build, test, script, lint or CI verification command executed** under `AGENTS.md`. Compiler correctness and runtime assertions are therefore unverified. Original SwiftData-to-Core Data user-data upgrade policy remains an unresolved release decision.

## Review-cycle reassessment (PR #157, first corrective cycle)

The review reported that `reorder` only captured `existingDefaultID` to prevent virtual built-in default inheritance, but never preserved the selected UUID when changing `sortOrder`/`updatedAt` on another flagged row. This is a **material affected part of the existing reorder/restore row**, not a new artificial fixture permutation. Audit of all sibling writes found that a real `upsert` of an existing physically flagged loser can likewise bump `updatedAt`, and `restoreDefaultColors` can update a nonpreferred built-in during canonical repair; all share the winner-preservation invariant. `deleteColors` can remove/hide the previously preferred row, so it must preserve the winner only while it survives visibly. `setDefaultColor` intentionally bypasses precedence and must remain unchanged. These sibling paths are covered by the existing matrix rows, expanded above **before production code updates**. A normal pristine White default, single physical default, and no-op write must retain their existing semantics. No migration, recovery, field-check/working or relationship changes are part of this correction.

## Review correction — final static reconciliation

- **Finding:** the earlier implementation captured the preferred default before a reorder but used that ID only for virtual built-in insertion. Moving the physically flagged losing color updated both its sortOrder and updatedAt, so it could become preferred after save, changing the default used by newly created animal tags. The correction now passes the pre-write selected ID into the existing `normalizeDefaults` before commit, preserving it while it remains a visible flagged row.
- **Complete affected write category:** `upsert` (including editing a physically flagged loser and an explicit incoming `isDefault` override), `deleteColors` (preserve surviving default, fall back if removed/hidden), `reorder` (including mixed virtual/persisted options and changed losing metadata), and `restoreDefaultColors` (canonical built-in repair and remapping) all capture the same pre-mutation preference before changing fields. Only the normalization helper and its callers change; `setDefaultColor` stays explicitly authoritative.
- **Normal no-op semantics:** read paths remain read-only; a partial reorder with no staged changes does not trigger a repair solely by passing a non-empty list. Existing stale Herd, failed write, rollback and multi-Herd boundaries remain enforced by unchanged transaction/core infrastructure.
- **New permanent contract evidence:** the existing Core Data Tag Color suite now exercises a physically flagged losing color reordered to index zero, then a virtual built-in reorder and restore; a separate case edits the losing color while it is still physically flagged and then explicitly selects another via upsert; another case repairs an outdated physically flagged built-in Blue while retaining the winning custom color and an unchanged custom control. Each checks physical flags through `fetchColor(id:)`, projected winner through `fetchColors()`, and fresh repository reads as applicable.
- **Self-review:** diff remains scoped to the Tag Color repository, existing Core Data contract runner, and this matrix. No new managed object, identity, tag reference remapping, SwiftData, cloud, user-data migration or UI behavior is added. The reviewer-reported production regression is addressed in source, with targeted tests authored but not executed.
- **Verification:** not run under `AGENTS.md` without explicit authorization. CI status is not treated as a substitute for an authorized executed test. Compilation and in-memory/SQLite execution still require verification.
