# Milestone 12 — deterministic maternal-offspring detail order

## Design and ownership

`CDAnimal.damOffspring` is an unordered Core Data relationship. `CoreDataAnimalProjection.detail` orders maternal offspring by descending birth date and ascending localized primary-tag number, but returns equal comparison for distinct calves with identical birth dates and tags (especially untagged calves). `AnimalDetailOffspringSection` renders that array directly. Equal-key children can therefore change visual positions after a fresh fetch or store reopen, despite unchanged durable identities. Keep the existing birth-date and tag priority; use the persisted offspring UUID as the final total-order tie-break. No write, model, domain, or navigation change is needed.

Review scope: `CoreDataAnimalRepository.fetchAnimalDetail` and `fetchAnimalAggregateForEditing` are the production detail readers. The repository's `create`, `update`, `addTag`, `updateTag`, `promoteTag`, `retireTag`, `addHealthRecord`, `addPregnancyCheck`, `createAnimal` and `updateAnimal` also return the shared `CoreDataAnimalProjection.detail` snapshot. `AnimalDetailViewModel` and `AnimalDetailView` render offspring through `AnimalDetailOffspringSection`; Animal editing consumes the same detail in aggregate snapshots. **Field Check also consumes the array:** `FieldCheckSessionDetailView` opens `FieldCheckAnimalDetailView`, whose `FieldCheckAnimalDetailViewModel.load`/`refresh` call the same `AnimalDetailRepository.fetchAnimalDetail`. The Field Check view renders `AnimalDetailOffspringSection` for both active and completed sessions; it refreshes after roster/finding mutations, pull-to-refresh, and Add Offspring sheet dismissal. The same shared detail-order contract covers both screen paths without a separate Field Check comparator or duplicate test. `CoreDataAnimalProjection.timeline` already has a source-ID tie-break and is not modified; `CoreDataReadModelActor` Dashboard offspring counts and list/lookup queries use separate projection/sort contracts (M9). Pasture and Working do not independently sort this maternal-offspring detail array.

## Static review and execution policy

Design-first audit traced the Core Data relationship, all 12 direct `CoreDataAnimalProjection.detail` entry points (two reads and ten mutation-return paths), ordinary Animal detail and Field Check session navigation → `FieldCheckAnimalDetailViewModel.load`/`refresh` → shared `AnimalDetailOffspringSection`, plus timeline sorting and M5/M7/M9 ownership. Field Check refresh after roster/finding mutations, pull-to-refresh and Add Offspring sheet dismissal re-reads the same stable projection; completed sessions render the same offspring section read-only. The existing SQLite regression protects shared `fetchAnimalDetail` immediately and after an independent read-only reopen, including aggregate editing; a duplicate test for a second view consuming that same snapshot is unnecessary. Extend the existing `CoreDataAnimalRepositoryContractTests` SQLite suite; do not create a separate fixture runner. Build, tests, scripts, lint and CI verification are not run unless explicitly requested by the user under `AGENTS.md`.

Legacy SwiftData upgrades remain an independent unresolved release decision; retain `Info/CORE_DATA_CUTOVER.md`.
