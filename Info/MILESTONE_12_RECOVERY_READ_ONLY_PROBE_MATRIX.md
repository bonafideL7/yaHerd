# Milestone 12 — Non-mutating Core Data Recovery Probe Matrix

## Design, callers, and ownership

The recovery center's `RecoveryModeController.checkPersistentStoreReadOnly()` is called from `RecoveryModeView` through the running app's recovery-only controller environment. Normal durable startup uses `yaHerdApp.bootstrap` → `CoreDataPersistentContainer.defaultStoreURL` → `CoreDataAppPersistenceAssembly.load`. The normal startup helper **intentionally creates** the application-support storage directory; using that helper from a read-only recovery check violates the check's non-mutating contract.

This slice keeps normal startup unchanged. The probe instead resolves the same filename under the already-known Application Support location without creating a directory, checks that the existing SQLite main file is a regular file, then opens it with the existing `.readOnly` Core Data assembly. The controller's existing injectable Application Support URL is used for both the inventory and the probe. The probe does **not** bootstrap a Herd, repair/import legacy records, replace an absent store, change recovery-mode policy, or promote an in-memory recovery session to writable mode. A successful probe only advises restarting.

**This PR owns:** recovery-check path resolution; non-mutating missing/non-file check behavior; the recovery-controller result and retry lifecycle; integration coverage against the real local SQLite assembly.

**Existing permanent owners:** M3 `CoreDataPersistenceFoundationTests.testReadOnlyStoreUsesSameStoreAndRejectsTransactions` owns actual store read-only enforcement; M4 bootstrap/identity contracts own Herd creation and one-Herd invariant; M10 `CoreDataAppHerdBootstrapperTests` owns recovery-mode policy, first-open legacy/journal protection, recoverable-file enumeration/export, and normal launch. M7–M9 own feature data integrity, mapper and read-projection correctness. Legacy SwiftData data upgrades and the final release decision remain separate.

## Static self-review / verification boundary

- Reconcile the controller's path construction with the production `defaultStoreURL` filename and the existing recovery file inventory; do not call the directory-creating production helper during the probe.
- Check the complete call chain from the recovery button through the controller; do not change normal startup, write policy, archive contents, or domain dependencies.
- Add integration regressions to the existing M10 Core Data app-bootstrap test suite rather than creating a new suite or an additional global verifier.
- Static review only. Do not run builds, tests, scripts, lint or CI without an explicit user request.
