# Milestone 12 — Working Treatment-Record Scope Identity Matrix

## Design (recorded before production edits)

The current direct `CoreDataWorkingRepository` validates queue UUIDs across the complete selected Herd, and `validateSessionGraph` rejects duplicate `CDWorkingTreatmentRecord` UUIDs **within** a session. A treatment record is nevertheless a Herd-owned application entity. Two different sessions in one Herd may contain distinct physical treatment rows with the same UUID and pass all existing direct read preflights. In the Working queue editor, `WorkingMapper.makeTreatmentRecordSnapshot` then projects that ambiguous UUID into `WorkingTreatmentRecordSnapshot.id` as an application identity. Session list/detail paths also accept the corrupt selected-Herd record set, even though they validate their per-session graphs.

Extend the **existing selected-Herd direct-read preflight**, once per operation, to check the complete `CDWorkingTreatmentRecord` cohort as well as queue items before mapping. Fail closed with `CoreDataPersistenceError.duplicateApplicationID(entity:id:herdID:)`; neither select a preferred row nor repair/modify physical records. Preserve legal reuse across different Herds and existing session, queue and treatment payload validation. A missing requested session/queue retains its current nil/not-found behavior. Reuse the current repository and the `CoreDataWorkingRepositoryContractTests` fixture/harness. Do not introduce another validator framework, schema constraints, read-model actor, migration, SwiftData, CloudKit or UI change.

**Ownership:** This PR owns complete selected-Herd **Working treatment-record** identity validation for the three direct read entry points and the corresponding file-backed contract. M8 owns treatment-record lifecycle, one-off treatment semantics, data replacement, transactional rollback, and session graph membership/payload validation. The immediately preceding M12 queue identity PR #166 owns queue UUID uniqueness; this change extends the same preflight without duplicating its regression. M5 owns general Animal health and pregnancy record identity and historical projections; they are shared Animal entities, not `CDWorkingTreatmentRecord` and are not changed by this PR. M9 owns bounded Home/Dashboard read-model query semantics. M3/M12 foundation owns physical SQLite scope and read-only store behavior. App forwarding, existing view-model error presentation, and navigation implementation are unchanged, but the broader read failure is observable: Finish and Collect pre-mutation session rechecks now fail closed, and startup Working-workflow restoration falls back to the sessions list. These are intentional consequences of the scoped integrity guard, not new mutation or navigation logic.

## Static trace and verification policy

Checked all three direct read entry points, the existing complete-Herd queue preflight, per-session treatment duplicate checks, `WorkingMapper`'s record identity projection and App forwarding. Traced `WorkingSessionDetailViewModel`, `WorkingFinishSessionViewModel`, the Finish view and `CompleteWorkingSessionUseCase` read-before-write, both `WorkingCollectAnimalsView` reads and save-error handling, navigation restoration fallback, initial `WorkingQueueItemEditorViewModel.load`, and all three secondary `WorkingSessionAnimalWorkView` detail calls: `seedSessionSourcePastureReferenceIfNeeded`, `refreshSessionSourcePastureAfterMutation`, `ensureSourcePastureReferenceForSave`. Seed/refresh silently retain form and stale/absent reference; fallback gives a generic save-verification error only when reached. With a cached source reference or explicitly selected destination, this new read guard does not guarantee blocking later editor writes. Also traced M8 work-data replacement. These callers need no production edit to fulfill this PR's **direct-read** scope; the PR's SQLite contract owns read integrity, and M8/navigation own UI state, mutation and route semantics. Auxiliary view-path behavior is statically traced and not claimed as a new executable UI test. The new regression belongs in `yaHerdTests/CoreData/CoreDataWorkingRepositoryContractTests.swift`, not a new global test runner. `AGENTS.md` disallows tests, builds, lint, scripts and GitHub Actions verification without an explicit user request, so compilation and SQLite execution remain unverified until authorized.
